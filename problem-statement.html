0x01

The problem

Tethering an Android phone to a computer over USB — faster than a Wi-Fi hotspot, less battery drain, one cable — is a non-event on Windows or Linux. On a Mac it quietly doesn't work, and the reason is a protocol mismatch.

When an Android phone toggles on "USB tethering," it presents itself to the computer as an RNDIS device — Microsoft's Remote NDIS, a way of tunneling Ethernet frames over USB. Windows and Linux ship an RNDIS host driver. macOS never has. Apple supports the standards-based cousins (CDC-ECM and CDC-NCM) and it supports iPhone tethering, but plug in an Android phone speaking RNDIS and the Mac sees a device it has no idea how to talk to. It appears in Network settings as SAMSUNG_Android — Not connected and just sits there.

0x02

The dead incumbent

For years the fix was HoRNDIS — a kernel extension that added the missing RNDIS host driver to macOS. It's genuinely gone: last release 2018, and it fails on any current Mac for two independent reasons.

  • Wrong CPU. It was only ever built for Intel x86_64. On Apple Silicon it can't even load — the binary is the wrong architecture for the M-series chip.
  • Wrong era. Apple has been dismantling third-party kernel extensions since 2019. On Apple Silicon they require reduced security and reboots, and recent macOS releases removed several of the low-level networking hooks HoRNDIS depends on outright.

Reviving it as a kext is a dead end. But the insight that made this project possible: HoRNDIS ran in the kernel because that's how you wrote drivers in 2012. The actual work it does — speak RNDIS, hand packets to the network stack — doesn't need the kernel at all. It can live entirely in userspace.

0x03

The detour that didn't pan out

Before writing code we tried the free lunch: modern Android can present the standards-based NCM protocol that macOS does understand. One ADB command — svc usb setFunctions ncm — and the Mac instantly saw a native network interface (en8). It genuinely worked, for a moment.

Then Samsung's firmware slammed the door. Every time the USB-tethering toggle is flipped, One UI force-resets the USB function back to RNDIS, killing the NCM interface. We confirmed it in the tethering service's own state: mUsbTetheringFunction: RNDIS, hardcoded, ignoring the system setting we changed. Worse, poking at the USB functions this way left a zombie network interface on the phone that came back to bite us later. NCM was out. Time to build.

0x04

What we built

A single C program that does everything HoRNDIS did, in userspace, using two ordinary building blocks: libusb to talk to the phone, and a utun device to hand packets to macOS. Nothing else. It compiles to a 54 KB binary.

How it actually moves a packet

The bridge opens the phone's two USB interfaces — a control channel and a data channel — and runs the RNDIS handshake: initialize, ask the phone for its MAC address, set a packet filter to start the flow. Then two threads pump traffic. Outbound, it reads an IP packet from utun, wraps it in an Ethernet frame and then an RNDIS header, and writes it to the phone's bulk USB endpoint. Inbound, it does the reverse. It also runs a tiny DHCP client to get an IP from the phone and answers ARP so the phone knows where to send replies.

0x05

The four walls

The control plane worked almost immediately — the handshake succeeded on the first try. Getting data to flow took four separate diagnoses, each with a symptom that looked nothing like its cause. This is the actual debugging story.

Wall 1 · silence on the wire

The kernel was holding the door

Control messages worked, but every bulk read timed out — zero bytes, forever. macOS had quietly attached its own CDC driver to the phone's interfaces and was consuming all the incoming data before we could.

FixExplicitly detach the kernel driver from both USB interfaces before claiming them, and re-attach on exit so macOS recovers cleanly.

Wall 2 · NO-CARRIER

Android was serving a ghost

The phone reported the tethering link as NO-CARRIER even though our handshake was perfect. The culprit was that zombie interface from the NCM detour: Android was running DHCP and routing on a dead usb0 left over from earlier, while the live USB connection was a brand-new rndis0 that was administratively down. It was answering the door of an empty house.

FixReboot the phone to clear the stale interface, then enable tethering only through the Settings UI — never by poking USB functions over ADB again.

Wall 3 · 1.5 Mbps ceiling

We were reading one packet, throwing away five

Data finally flowed — but crawled. Android bundles multiple RNDIS packets into a single USB transfer for efficiency. Our receive code extracted only the first packet in each transfer and discarded the rest. Every dropped packet triggered a TCP retransmit; throughput collapsed to a trickle.

FixRewrite the receive path to walk every concatenated packet in a transfer, carrying leftover bytes across reads.

Wall 4 · 7 KB/s black hole

The VPN shrank the envelope

Turning on a VPN on the phone made it worse — 7 KB/s. Classic MTU black hole: the VPN wraps every packet in extra headers, shrinking the real usable packet size, but the bridge was still advertising a full 1500-byte MTU. Small handshake packets fit; large data packets were silently dropped with nowhere to fragment.

FixLower the interface MTU to 1400 (a new --mtu flag) so packets fit inside the VPN's envelope. Throughput jumped ~37,000×.

0x07

Using it

The routine, start to finish:

  • Plug in the phone and enable USB tethering from Settings (this leaves it in RNDIS mode — exactly what we want).
  • Run sudo ./macdroid-tether-extreme --default-route. Add --mtu 1400 if a VPN is running on the phone.
  • Turn off Wi-Fi. All traffic now flows over USB. The terminal window is the driver — keep it open.
  • Press Ctrl+C when done. It restores your previous default route and DNS and cleans up the interface.
One rule

Never switch USB functions with svc usb setFunctions to force NCM — that's what created the zombie interface behind Wall 2. Use the Settings toggle, full stop.

0x08

A note on carrier detection

How can a carrier even tell traffic is tethered? Three main signals — and understanding them explains why a VPN on the phone changes the picture:

  • TTL / hop count. Every IP packet has a counter that drops by one at each router. Traffic born on the phone leaves at the OS default; tethered traffic passes through the phone first, so it arrives one lower. Seeing that off-by-one is the classic tell.
  • OS fingerprinting. A Mac's TCP options, TLS handshake, and user-agent strings look nothing like a phone's. Desktop signatures on a phone line stand out.
  • Endpoints & volume. Hits to desktop-only services, or simply blowing past a hotspot data bucket, flag the session.

A VPN running on the phone hides the first two — everything becomes uniform, phone-originated, encrypted packets to a single endpoint. The catch is the overhead it adds, which is precisely what the --mtu 1400 fix accommodates. The two interact, which is why the order they're debugged in matters.
